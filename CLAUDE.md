# Car Launcher — контекст для Claude

Лаунчер (домашний экран) для китайской Android-магнитолы пользователя.
Образец — CarCar: на главном экране несколько **живых окон** приложений
(навигатор, музыка, TPMS и т.п.), которые можно двигать и менять в размере.

Общение с пользователем — **на русском**. Пользователь не программист:
тестирует на магнитоле, присылает фото экрана. После каждой правки нужна
готовая ссылка на APK из GitHub Release (см. «Сборка»).

**Правило работы (по просьбе пользователя): коммитить и пушить сразу в `main`**,
без отдельных веток и pull request. APK собирается только из `main`, а
пользователю нужна установка сразу. Порядок после каждой правки:
коммит → push в `main` → дождаться сборки → проверить, что она успешна →
дать пользователю ссылку на страницу релиза `build-N` (см. «Сборка»). Если сборка упала —
прочитать аннотации, исправить, повторить, и только потом отвечать.

## Устройство

- Android 10/11, вертикальный экран «тесла»-формата (портрет).
- Внизу экрана — **системная панель климата прошивки**, поверх всего.
  Окна не должны под неё заходить: запас снизу настраивается
  (`SettingsService.bottomReserve`, по умолчанию 150 px), применяется ко всем
  экранам в `MaterialApp.builder` (`lib/app.dart`).
- Слева висит плавающая кнопка прошивки (быстрый доступ) — это не наше.
- **Прошивка подписана публичным тестовым ключом AOSP.** Поэтому APK,
  подписанный `platform.pk8` из AOSP, с `sharedUserId="android.uid.system"`
  ставится и работает с UID 1000. На этом держится всё: ActivityView,
  привязка виджетов без диалога и т.д. Рут не нужен.
- Эмулятор для проверки не годится: там `INSTALL_FAILED_SHARED_USER_INCOMPATIBLE`
  (другой ключ платформы) — это ожидаемо. Проверка только на магнитоле.

## Архитектура

Flutter (UI) + Kotlin (нативная часть), связь — MethodChannel `car_launcher/native`.

Репозиторий хранит **не полный Flutter-проект**, а только исходники:
- `lib/` — весь Dart-код.
- `android_overlay/` — Kotlin-файлы, AndroidManifest, res; копируются поверх
  сгенерированного проекта.
- `pubspec_extra.yaml` — доп. зависимости; `scripts/patch_project.py` вставляет
  их в сгенерированный `pubspec.yaml` и пишет `pubspec_overrides.yaml`.

Ключевые файлы:
- `android_overlay/kotlin/.../MainActivity.kt` — обработчики канала, жизненный
  цикл (onPause: `clear()` окон или `hide()` по настройке `keep_windows_bg`),
  onActivityResult для настройки виджетов.
- `AppWindowHost.kt` — живые окна: прозрачный оверлей `FrameLayout` поверх
  FlutterView в `android.R.id.content`; в нём `WindowFrame` с
  `android.app.ActivityView` (через рефлексию) или `AppWidgetHostView`;
  нативная «пилюля» с часами (TextClock) сверху. `sync(specs, pill)` —
  добавить/убрать/подвинуть окна; `hide()` — спрятать оверлей без уничтожения;
  `clear()` — уничтожить всё (ActivityView.release).
- `WidgetSupport.kt` — AppWidgetHost/Manager (HOST_ID 0x0CA4, REQUEST_CONFIGURE 7341).
- `lib/screens/home_screen.dart` — главный экран: раскладка окон в долях экрана
  (`WindowRect`), режим правки (перетаскивание/размер, до 4 окон), меню по
  нажатию на пилюлю, синхронизация живых окон (`_syncLiveWindows`), выбор
  содержимого окна (приложение или виджет).
- `lib/services/preset_service.dart` — что назначено окну: пакет приложения
  ИЛИ виджет (id + название). Слоты `window_1..window_4`.
- `lib/services/preset_service.dart` также хранит **сохранённые пресеты**
  (`layout_presets_v1`, модель `lib/models/layout_preset.dart`): раскладка +
  пилюля + содержимое окон. Экран `lib/screens/presets_screen.dart`, быстрое
  переключение — чипы в меню пилюли. Виджет из системы удаляется, только
  если он не стоит ни в окне, ни в одном пресете (`widgetInUse`).
- `lib/services/settings_service.dart` — раскладка, положение пилюли, запасы
  сверху/снизу, тема, переключатели:
  - `keep_windows_in_launcher` (по умолч. false) — при настройках/меню/выборе
    приложения только прятать окна, а не пересоздавать;
  - `keep_windows_bg` (по умолч. false) — то же при уходе лаунчера в фон
    (ключ читает нативная сторона из `FlutterSharedPreferences` как
    `flutter.keep_windows_bg`).

Два режима работы:
- **Живые окна** (системный UID есть) — основной, у пользователя работает он.
- **Запасной** (нет системных прав) — приложения открываются свободными окнами
  (freeform, нужна опция разработчика). Пользователю не нужен, но код есть.

## Сборка

Только через GitHub Actions (`.github/workflows/build-apk.yml`), локально
Flutter SDK нет и скачать его из окружения нельзя.

Пайплайн: `flutter create` (свежий скаффолд под версию Flutter на раннере) →
копия `lib/` и `android_overlay/` → `patch_project.py` → `pub get` →
`flutter analyze` → `flutter build apk --release` → переподпись `apksigner`
ключом AOSP `platform.pk8/x509` (из aosp-mirror/platform_build) →
GitHub Release `build-N` с `car-launcher-build-N.apk`.

В том же релизе — **демо-сборка** `car-launcher-demo-build-N.apk`
(шаг «Build demo APK»): без `sharedUserId`, без HOME, applicationId
`com.carlauncher.app.demo`, подпись AOSP `testkey`. Ставится на любой
телефон/эмулятор рядом с основной; живых окон нет (запасной режим) —
чтобы смотреть и настраивать интерфейс без магнитолы.
У пользователя демо стоит в эмуляторе Android Studio «Medium Tablet», API 30.

**Ссылку пользователю давать на страницу релиза**
(`https://github.com/lancer19981991-arch/car-launcher/releases/tag/build-N`,
там «Assets» → `car-launcher-build-N.apk`). Прямая ссылка на файл у него
не скачивается (сервер файлов GitHub плохо доступен), страница релиза — работает.
Загрузить APK в Google Диск через коннектор нельзя (файл передаётся целиком
в сообщении, 50 МБ не влезает).

Каждый push в `main` = новая сборка (кроме коммитов, где менялись только `*.md`). Номер N = номер запуска, неудачные
запуски тоже съедают номера.

Как следить и получить ссылку (только REST, GraphQL недоступен):
```bash
id=$(gh api "repos/lancer19981991-arch/car-launcher/actions/runs?per_page=1" --jq '.workflow_runs[0].id')
gh run watch $id -R lancer19981991-arch/car-launcher --exit-status --interval 20
gh api "repos/lancer19981991-arch/car-launcher/releases?per_page=1" \
  --jq '.[0] | .tag_name, (.assets[] | .browser_download_url)'
```

**Логи Actions из окружения Claude недоступны** (домен blob-хранилища закрыт).
Поэтому ошибки дублируются в **аннотации**, они видны через API:
```bash
jid=$(gh api repos/lancer19981991-arch/car-launcher/actions/runs/$id/jobs --jq '.jobs[0].id')
gh api repos/lancer19981991-arch/car-launcher/check-runs/$jid/annotations --jq '.[].message'
```
Скачать APK самому: `gh api -H "Accept: application/octet-stream" .../releases/assets/{id}`.

Компилятора локально нет — перед push хотя бы проверять баланс скобок
и внимательно перечитывать diff.

## Грабли, на которые уже наступили

- **shared_preferences_android 2.5.0** (17.10.2026) перешёл на JNI и в
  release-сборке падает при старте (`NoSuchMethodError ... getAll`) → белый
  экран. Закреплён диапазон `>=2.4.0 <2.5.0` через `pubspec_overrides.yaml`
  (в `patch_project.py`). Версии 2.4.29 на pub.dev нет. Зависимости
  в pubspec не закреплены — новые версии плагинов могут ломать сборку внезапно.
- На случай падения в `main.dart` есть экран с текстом ошибки (тёмно-красный)
  и `ErrorWidget.builder` с текстом — пользователь присылает фото, по нему
  видна причина.
- `addPostFrameCallback` без кадра не срабатывает: `_scheduleSync()` обязательно
  вызывает `scheduleFrame()`, иначе после неподвижного экрана окна не появятся.
- После закрытия экрана поверх (настройки) идёт анимация перехода, главный
  экран масштабирован → координаты окон неверные (окна «съезжают»). Решение —
  пересинхронизация с задержкой 450 и 1200 мс (`_syncAfterTransition`).
  Попытка слушать `ModalRoute.secondaryAnimation` откатана.
- **Долгое нажатие на живое окно с приложением не работает**: на Android 10
  касания по ActivityView идут прямо во встроенный дисплей, мимо лаунчера.
  Сменить приложение — через режим правки (кнопка ⚙ на окне). Для виджетов
  долгое нажатие может работать (`WindowFrame.dispatchTouchEvent`).
- Если окна только прятать (`hide`), ActivityView держит задачи приложений на
  виртуальных дисплеях. Возможный риск: приложение, запущенное отдельно,
  «откроется» на спрятанном дисплее. Поэтому по умолчанию окна пересоздаются.
- Шаблонный `test/` от `flutter create` ломает analyze (ссылка на MyApp) —
  удаляется в workflow.
- `isSystemApp` определять через `Process.myUid() == SYSTEM_UID`, не по FLAG_SYSTEM.
- Эмулятор x86 (32-bit) → NO_MATCHING_ABIS; нужен x86_64/arm64 (но см. выше —
  на эмуляторе всё равно не встанет из-за ключа).

## Что сделано (по пользовательским запросам)

- Нет дока с ярлыками, минимум интерфейса; верхняя панель заменена
  полупрозрачной «пилюлей» с часами (перетаскивается в режиме правки,
  нажатие — меню: правка раскладки / настройки).
- Свободная раскладка: до 4 окон, двигать, менять размер, добавлять/удалять;
  окна никогда не заходят под панель климата.
- В окно можно поставить приложение или **виджет рабочего стола**
  (у TPMS пользователя виджета не оказалось — стоит само приложение).
- **Пресеты** раскладок (build-29): сохранить / переключить из меню пилюли /
  переименовать / удалить. Пользователь проверил: окна встают на места,
  содержимое верное, под климат-панель не заходят.
- **Подсветка контура окон** (Настройки → Оформление): цвет из палитры
  `SettingsService.borderColors` или «нет» (по умолч.), толщина 1–8 px.
  Flutter рисует рамку+свечение у карточек; в живом режиме рамку рисует
  нативная сторона (`AppWindowHost.BorderSpec`, `styleFrame`: stroke + padding
  у `WindowFrame`), передаётся в `syncAppWindows` полем `border`.
  Ещё: скругление углов 0–40 px (`windowCornerRadius`, по умолч. 16) и сила
  свечения 0–100% (`windowGlow`, по умолч. 50%), палитра — 22 оттенка.
  Нативно поверхность ActivityView скругляется скрытым `setCornerRadius`
  (через рефлексию; если метода нет — внутри рамки прямые углы).
- **Погода в пилюле** рядом с часами («☁ +5°»): `lib/services/weather_service.dart`,
  Open-Meteo (без ключа; `dart:io` HttpClient, без новых пакетов), обновление
  раз в 20 мин и при возврате на экран. Место — город из настроек
  (поиск через geocoding-api.open-meteo.com) или `getLastLocation` (нативно,
  LocationManager.getLastKnownLocation). Пилюля шире (172 вместо 104), когда
  есть погода; нативной пилюле текст идёт в `pill.weather`. В манифест
  добавлены INTERNET и ACCESS_*_LOCATION.
  Запасные источники (если Open-Meteo недоступен): погода — api.met.no,
  поиск города — nominatim.openstreetmap.org (оба требуют User-Agent).
  Ошибки показываются понятно (`WeatherService.describeError`). Из окружения
  Claude эти хосты закрыты прокси — проверить можно только на устройстве.
  build-34 в эмуляторе давал «нет связи» (браузер при этом Open-Meteo
  открывал), в build-35 (с запасными источниками) погода заработала —
  какой именно источник сработал, неизвестно.
  **Яндекс.Погода** — по личному ключу пользователя (лимит 500 запросов/сутки,
  у нас ~75): Настройки → Погода → «Ключ Яндекс.Погоды» (`weather_yandex_key`).
  Если ключ задан — Яндекс первым (`/v2/forecast`, ключ в заголовках
  `X-Yandex-Weather-Key` и `X-Yandex-API-Key`), при сбое — Open-Meteo, met.no.
  В настройках видно источник («Сейчас: ☁ +5° (Яндекс)») и ошибку Яндекса.
  После неудачи повтор через 1–3 мин, а не через 20.
  Пользователь проверил (build-36): ключ принят, погода идёт от Яндекса.
